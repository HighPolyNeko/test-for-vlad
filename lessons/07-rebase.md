# Урок 7. rebase — переписать историю

## Merge vs Rebase

Ты сделал ветку `feature` от `main`, а в `main` за это время появились новые коммиты:

```
         C──D        feature
        /
A──B──E──F           main
```

**Merge** (`git merge main`, находясь в `feature`) создаёт merge-коммит M с двумя родителями:

```
         C──D──M     feature
        /     /
A──B──E──F────       main
```

**Rebase** (`git rebase main`, находясь в `feature`) **переигрывает** твои коммиты поверх нового `main`:

```
A──B──E──F──C'──D'   feature
          main
```

`C'` и `D'` — **новые коммиты с новыми хешами**. Старые `C` и `D` остаются в reflog (урок 9).

| | merge | rebase |
|---|---|---|
| История | честная, с «ромбиками» | линейная, как будто всё писали по очереди |
| Хеши коммитов | не меняются | меняются |
| Безопасно для общих веток | да | **нет** |
| Конфликты | решаешь один раз | можешь решать для каждого коммита заново |

## 🥇 Золотое правило

> **Не ребейзь коммиты, которые уже есть у других людей.**

Если ты переписал запушенную ветку, с которой работает кто-то ещё, у него
останутся старые коммиты, а у тебя новые. Получится каша из дублей.
Свою личную фичевую ветку ребейзить можно, общую (`main`, `develop`) нельзя.

## Interactive rebase — причесать свои коммиты перед PR

```bash
git rebase -i HEAD~4      # редактировать последние 4 коммита
git rebase -i main        # все коммиты ветки, которых нет в main
```

Откроется редактор со списком (сверху — **старые**, снизу — новые, наоборот от `git log`!):

```
pick 1a2b3c4 feat: список фильмов
pick 5d6e7f8 wip
pick 9a8b7c6 fix typo
pick 3c4d5e6 ещё фильм
```

Меняешь слово в начале строки:

| Команда | Что делает |
|---|---|
| `pick` | оставить как есть |
| `reword` | оставить, но поменять сообщение |
| `edit` | остановиться на коммите, чтобы поправить его содержимое |
| `squash` | склеить с предыдущим, сообщения объединить |
| `fixup` | склеить с предыдущим, сообщение этого коммита выкинуть |
| `drop` | выкинуть коммит совсем |
| переставить строки | поменять порядок коммитов |

### Лайфхак: `--fixup` + `--autosquash`

```bash
git commit --fixup 1a2b3c4          # создаст коммит "fixup! feat: список фильмов"
git rebase -i --autosquash main     # git сам поставит его под нужный коммит с пометкой fixup
```

## После rebase — пуш только с force

История поменялась, обычный `git push` откажет. Нужно:

```bash
git push --force-with-lease     # ✅ так
git push --force                # ❌ так лучше не делать
```

`--force-with-lease` перезапишет ветку, **только если на сервере она такая же, какой ты её видел
последний раз**. Если коллега успел запушить туда что-то своё, пуш упадёт, и ты не затрёшь его работу.
`--force` затирает молча.

## Конфликты при rebase

```bash
# правишь файл
git add <файл>
git rebase --continue    # к следующему коммиту
git rebase --skip        # выкинуть текущий коммит
git rebase --abort       # вернуть всё как было до rebase
```

> ⚠️ **Неочевидно:** при rebase `ours` и `theirs` **меняются местами**.
> Rebase переносит твои коммиты поверх чужой ветки, поэтому `ours` — это ветка, *на которую*
> ребейзишь (например, `main`), а `theirs` — **твои** коммиты. При merge наоборот.

## Полезное

```bash
git pull --rebase                   # подтянуть main без merge-коммита "Merge branch 'main' of ..."
git config --global pull.rebase true  # делать так всегда
git rebase --onto main old-base feature  # пересадить ветку: взять коммиты feature после old-base и поставить на main
```
