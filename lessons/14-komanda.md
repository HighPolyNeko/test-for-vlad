# Урок 14. Git в команде: процессы и правила

## Модели ветвления

| Модель | Как устроена | Где встречается |
|---|---|---|
| **GitHub Flow** | `main` всегда рабочий. Всё делается в короткоживущих ветках → PR → мерж → деплой | веб-сервисы, большинство стартапов |
| **Git Flow** | `main` (релизы) + `develop` (разработка) + ветки `feature/*`, `release/*`, `hotfix/*` | продукты с редкими версиями: мобилки, десктоп, коробки |
| **Trunk-based** | все мержат в `main` маленькими порциями (хоть несколько раз в день), недоделки прячут за feature flags | большие компании с сильным CI |

Релизные ветки + cherry-pick хотфиксов (урок 6) встречаются и в GitHub Flow, если нужно
поддерживать старые версии.

## Сообщения коммитов: Conventional Commits

```
<тип>(<область>): <что сделано>

feat(auth): вход через Google
fix(cart): не пересчитывалась сумма при удалении товара
docs: обновил README
refactor, test, chore, perf, ci, build...
feat!: ... или "BREAKING CHANGE:" в теле — ломающее изменение
```

Зачем: история читается, а changelog и номер версии можно генерировать автоматически.

## Версии: SemVer

`MAJOR.MINOR.PATCH`, например `2.4.1`:
- **PATCH** (`2.4.1` → `2.4.2`) — багфикс, ничего не ломает;
- **MINOR** (`2.4.1` → `2.5.0`) — новая функциональность, обратно совместимая;
- **MAJOR** (`2.4.1` → `3.0.0`) — ломающие изменения.

👀 В этом репо: тег `v1.0.0` и хотфикс `v1.0.1`, вкладка **Releases**.

## Хороший PR

- **Маленький.** 200 строк внимательно отревьюят, 2000 строк пролистают.
- Одна задача — один PR. Рефакторинг отдельно от фичи.
- Описание: **что** сделано, **зачем**, **как проверить**. Ссылка на задачу (`Closes #42` закроет issue при мерже).
- Перед PR подтяни `main` (merge или rebase) и почисти коммиты (`rebase -i`).
- Draft PR — «ещё не готово, но посмотрите направление».

## Защита main (Settings → Branches / Rulesets)

- Нельзя пушить напрямую, только через PR.
- Нужно N апрувов, зелёный CI, разрешённые конфликты.
- Запрет force-push.
- **CODEOWNERS** (`.github/CODEOWNERS`) — автоматически назначает ревьюеров по путям:
  ```
  /frontend/  @ivan
  *.sql       @db-team
  ```

## 🚨 Закоммитил секрет (пароль, токен, ключ)

1. **Сразу отзови и перевыпусти секрет.** Это главное.
2. Удаление в новом коммите **не помогает**: секрет остаётся в истории.
3. Переписывание истории (`git filter-repo`, BFG) + force-push тоже **не гарантия**: форки,
   клоны у коллег, кэши. Поэтому пункт 1 обязателен всегда.
4. Секреты хранят в `.env`, который лежит в `.gitignore`, или в секрет-хранилищах. В репо кладут только `.env.example`.

## Что никогда не делать в общей ветке

- `push --force` (если очень нужно, то только `--force-with-lease` и с предупреждением команды);
- rebase / amend уже запушенных коммитов;
- коммитить большие бинарники (для них есть **Git LFS**) и сгенерированные файлы (`node_modules`, `build/`).
