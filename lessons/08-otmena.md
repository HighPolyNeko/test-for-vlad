# Урок 8. Как отменять: restore, reset, revert, amend

Главный вопрос: **изменения уже запушены или ещё нет?**

- **Не запушено** → можно переписывать историю (`reset`, `amend`, `rebase`).
- **Запушено в общую ветку** → только `revert`, то есть новый коммит, который отменяет старый.

## restore — файлы

```bash
git restore file.md            # выкинуть незакоммиченные правки в файле (безвозвратно!)
git restore --staged file.md   # убрать файл из staging, правки остаются
git restore --source=HEAD~3 file.md  # достать версию файла трёхкоммитной давности
```

## reset — передвинуть ветку

`git reset <коммит>` передвигает **текущую ветку** на указанный коммит.
Разница между режимами — в том, что происходит с изменениями из «отброшенных» коммитов:

| Режим | Ветка | Staging | Рабочая папка | Когда использовать |
|---|---|---|---|---|
| `--soft` | ✅ передвинута | изменения **остаются в staging** | не трогается | склеить несколько последних коммитов в один |
| `--mixed` (по умолчанию) | ✅ | очищен | изменения **остаются в файлах** | переделать коммиты по-другому |
| `--hard` | ✅ | очищен | **всё стёрто** | выкинуть всё начисто ⚠️ |

```bash
git reset --soft HEAD~3 && git commit -m "одно нормальное сообщение"   # сквош без rebase -i
git reset HEAD~1           # отменить последний коммит, правки остаются в файлах
git reset --hard origin/main   # сделать локальную ветку точно как на GitHub
```

> ⚠️ `reset --hard` удаляет **незакоммиченные** изменения насовсем. Закоммиченные можно
> вернуть через reflog (урок 9), а незакоммиченные — нет.

## amend — поправить последний коммит

```bash
git commit --amend -m "новое сообщение"
git add forgotten.md && git commit --amend --no-edit   # докинуть забытый файл
```

`amend` создаёт **новый** коммит вместо старого. Если старый уже запушен, дальше
понадобится `push --force-with-lease`. В общих ветках так не делают.

## revert — безопасная отмена

```bash
git revert <hash>
```

Создаёт **новый** коммит с обратными изменениями. История не переписывается,
поэтому это единственный нормальный способ отменить что-то в `main`.

### Revert merge-коммита: `-m 1`

У merge-коммита **два родителя**, и git не знает, относительно какого из них откатывать:

```bash
git revert -m 1 <merge-hash>   # 1 = первый родитель, то есть main до мержа
```

`-m 1` значит: «оставь как было в `main`, выкинь то, что принесла ветка».

### 🪤 Ловушка: revert мержа и повторный мерж

Откатил мерж ветки `feature` через revert, в ветке всё починил и мержишь снова. **Старые коммиты
ветки не вернутся!** Git считает, что они уже влиты: они есть в истории, просто их изменения отменены.

Решение — сначала **revert того revert'а**, потом мерж фиксов:

```bash
git revert <hash-revert-коммита>
```

## 👀 Вживую в этом репо

Во вкладке Pull requests есть пара:
1. PR «Совет про push» — в шпаргалку попал **вредный** совет «если пуш не проходит, делай `git push --force`».
2. PR «Revert …» — этот мерж откатили через `git revert -m 1`. Совет исчез, а история осталась честной:
   видно и сам ошибочный мерж, и его откат.
